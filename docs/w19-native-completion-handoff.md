# W19 native job completion handoff

This change prepares a bounded crew-tools handoff to the **existing native form `7HCRlKJs4VZx4KwNmDa6`, EGC Job Completion Confirmation**. The native coordinator verified its saved version 4, seven required fields, prefill and desktop/mobile layout without submission. Workflow `1fbd6b3e-d5fb-422f-ba33-ae437c3e92f7` has the correct form trigger and remains unpublished. This is separate from PR #130's optional completion tag. A tag, contact note or workflow enrollment does not substitute for the native Form Submitted trigger.

## Implemented boundary

1. `GET /api/field-completion-handoff?jobId=...` requires the current authenticated **assigned job lead**, including for managers. It checks the canonical job's applied `complete` event, required checklist, verified original before/after photos, work notes, issue details and original completion time. Existing broad permission to mark work complete does not authorize this lead confirmation.
2. The lead deliberately prepares the handoff with `POST /api/field-completion-handoff`. A root-independent business key binds one record to `(canonical job ID, completion request ID, native form ID)`. An opaque reference uses the existing purpose-key root with its own `egc/w19-completion-ref/v1` label. Repeated taps, lost local responses and signing-key rotation reuse that record. The original closeout actor and confirming lead are recorded separately.
3. Only the verified native launch URL and verified prefill keys are used. The link contains the job ID, opaque reference and exact linked contact ID. The reference is a **sensitive bearer capability**. The link carries no notes, amounts, payment evidence, API key or session credential. The crew page keeps it only in memory, clears it on account/render/offline changes and requires a separate deliberate click. It does not submit the form automatically. Other required native answers are entered/reviewed by the lead; they do not replace saved canonical closeout facts.
4. The native **Form Submitted** workflow must call `POST /api/w19-completion-gate` with `{ "reference": "<completion reference lookup hint>", "contactId": "<current workflow contact ID>" }` before any consequential W19 action. An optional `submissionId` may be supplied only from a verified immutable receipt source. These property names are this Hub API's contract, not guesses at native merge fields. The picker has verified `{{contact.egc_completion_reference}}`; it is only a lookup hint. The actual current-contact picker token must also be verified.
5. The server reads HighLevel's documented `GET /forms/submissions` using existing credentials and the configured location. Search is only a hint: it verifies the actual receipt, form, contact, job and reference. It checks the provider creation time against the seven-day issuance window, exhausts bounded pagination and rejects unknown/truncated/malformed responses. Without a supplied receipt ID it selects the earliest exact matching provider receipt by creation time then ID, after validating the complete bounded result. Genuine duplicates still share one business claim. A supplied receipt ID must match strictly; it never falls back to another receipt. Date-only search bounds are padded by one day because provider date-filter timezone is unspecified; accepted receipt instants remain strictly bounded. There is no provider write or guessed form submission endpoint. A mutable contact reference cannot identify which event launched the workflow; it may leave an earlier job pending, so job-specific reconciliation remains necessary.
6. The gate rechecks current lead account/assignment, job/contact/location and immutable closeout proof after the provider read. The job revision and completion event are transaction-fenced. The business claim and provider submission claim are updated atomically. Exactly one successful response can return **boolean `proceed: true`**. Duplicates and uncertain commit responses return `proceed: false`; a different second native submission cannot release another task.

## W19 action and trusted values

The workflow must branch on **HTTP success plus exact boolean `ok === true` and `proceed === true`**, never merely the HTTP status or nonempty response. All other branches stop and expose an operations review item. A native submission by itself is not authorization. Re-entry and action retry settings must honor this gate on every run.

The single release returns canonical `jobId`, exact linked `contactId`, actual `completedAt`, its `America/Denver` calendar date, original completion actor, confirming lead, verified work/issue notes, and integer-cent balance values. The date is derived from saved work completion, never the scheduled date, browser clock or form submission date. The canonical completion/event and server-only handoff `completionSnapshot` store job-specific date and notes; mutable contact custom fields are not their storage authority.

If the job has a saved opportunity ID, the server reads exactly that opportunity and verifies its ID, contact and location. Success returns top-level `opportunityId` plus `opportunity: {status: 'verified', canUpdate: true, id: ...}`. A job without a saved ID returns null plus `canUpdate: false`; no newest/triggering/contact-wide opportunity is guessed. Downstream Find Opportunity must filter the exact returned ID, and stage writes must branch after the trusted balance: positive balance may use **EGC Pipeline → Job Completed Balance Due**; a zero balance must not be labeled balance due. A fully paid branch must still use confirmed money, not completion, before **Paid in Full—Completed**. This code performs no stage write.

`w19Balance()` reads the existing job-scoped money model. It requires a current approval/acceptance with its own timestamp and amount equal to the current quoted base. Supplied revision/fingerprint bindings must match. Current legacy approvals without those optional bindings are accepted only when their own dated amount reconciles. Approved changes come from the unified billed change-order model. Payment receipts must be verified and reconcile completely; tips do not reduce the work balance, and refunds/conflicts/unknown receipts require review. Balance is the approved total minus confirmed applied payments, clamped at zero. No public form amount is accepted.

W19's authorized action is an **internal task for Cesar to send the balance invoice**, using this trusted job-scoped result. It is not automatic invoice delivery. Preserve `taskMarker` (`egc-w19:<reference>`) verbatim in the task's durable evidence so operations can reconcile that exact job/task. Native evidence confirms the existing assignee is Cesar Joven; no recipient ID is invented here. Its due-date Value/Unit are empty, and the UI only offers Days/Weeks/Months/Years plus a time selector. A promised deadline within one staffed hour needs an explicit staffing calendar, deadline policy and supported computed due-time path. These are not inferred from the 9:30 job-start rule. Task delivery stays gated until the due-time and exact provider receipt/reconciliation procedure are verified.

No code in this change marks payment collected, an invoice paid, commission earned/payable, customer acceptance or customer-message approval. It does not activate a workflow. Existing 25%/75% terms remain: deposit due on the later of walkthrough date and seven days before job date; remainder due on the job date. Completion does not alter those due rules.

## Uncertain outcomes and recovery

Records are server-only under `w19CompletionHandoffs`, `w19CompletionClaims` and `w19CompletionSubmissions`; existing deny-by-default Firestore rules apply, with no permission change. Only `job.w19CompletionHandoff` operational metadata is patched on the job. Existing lifecycle, financial records and completion sync are preserved.

Provider read failures remain `prepared`, with a visible verification message; a later workflow gate call may safely read again. The Hub never resubmits the native form. After a durable release, status is **`released_unconfirmed` / task `unknown`** until operations reconciles exact provider task evidence. The crew page explicitly says Cesar's task is not confirmed. There is no automatic claim reset or task retry. A lost gate response can therefore stop the task from being created; that is a visible reconciliation case, never permission to create another task blindly.

This change intentionally does **not** claim a task was created merely because a native submission or gate release exists. Automated task acknowledgement/reconciliation is not implemented without a verified supported native workflow receipt contract. If that contract is unavailable, use exact-marker operations reconciliation and keep activation off until the owner accepts that recovery procedure. Expired intents, changed lead/contact/location, cancellations, deleted jobs or changed closeout evidence require operations review; they do not generate a fresh reference automatically. Historical jobs are untouched unless an authorized lead explicitly prepares a verified closeout.

Focused tests cover lead/crew/manager access, current account/origin, canonical evidence, duplicate taps/submissions, concurrency, signing-key rotation, stale revisions, contact/location/lead changes, cancellation/deletion, provider read failures and recovery, unknown release acknowledgement, immutable completion semantics, trusted money separation, request/response bounds and crew sign-out/offline/render races. The documented provider interface is [Get Form Submissions](https://marketplace.gohighlevel.com/docs/ghl/forms/get-forms-submissions/). The [Forms API catalog](https://marketplace.gohighlevel.com/docs/ghl/forms/forms/) does not document a form-submission creation endpoint, so this implementation uses an explicit human native form launch.
