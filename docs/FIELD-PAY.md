# FIELD-PAY: field balance collection and review

FIELD-PAY is completion of an existing queued unit. This runbook records the current implementation contract; it does not claim that the earlier unpublished candidate passed review, that this completion has passed final CI, or that live collection is enabled.

## Staff workflow

1. The assigned crew lead opens the job's **Payment** section in `/crew/job.html` while online. The server supplies the current unified balance, assignment, lead permission and payment holds. A manager can reach the same section from **Employee Hub → Estimates & payments → Review field payment** on the job's finance row.
2. **Card:** the lead opens Stripe Checkout for the **exact remaining service balance**; an optional tip is separate. Stripe collects the card details. A successful return or webhook must verify and record the charge on the job once. A cancelled, open or unknown checkout is not proof of payment. Check the existing Stripe session before another collection.
3. **Cash or check:** the lead enters the amount actually received (up to the current balance), a receipt or check reference, and a photo. The browser resizes the image; the server accepts at most **400 KB** of JPEG, PNG or WebP image bytes. Submission creates a pending private receipt and locks further collection; it does **not** increase verified money or close the balance.
4. An owner or manager opens **Review field payment**, views the private receipt, checks the amount and reference against the job, and approves or rejects with a reason where required. Approval uses the existing server money action and ledger, with the receipt decision and job lock release in the same Firestore commit. A changed balance, another payment review or a changed receipt stops approval for a fresh check. Rejection releases the pending lock without recording payment.
5. After a verified card charge or approved cash/check receipt, check the HighLevel payment-received handoff. If its status is pending or failed, the manager uses **Retry HighLevel handoff** from the same Payment section and checks for synced status. This retries CRM synchronization of the **already recorded** payment; it is not another charge or money entry. HighLevel remains responsible for customer messaging.

## Interrupted requests and holds

- The phone keeps a request ID for each pending submission, review, cancellation or CRM retry. After a lost response, use **Check current status** and then **Retry same action** with that ID. Reopening the saved job or Stripe session is safer than starting a second payment. A reused ID with different details is refused.
- One durable exact-balance card claim per job is saved before Stripe is called. A retry reuses the same Stripe idempotency key and parameters. If Stripe's outcome is still unknown at **23 hours**, recovery stops before Stripe could have pruned that key; the checkout remains held for operations reconciliation. Stripe documents that keys can be removed after 24 hours and a reused pruned key creates a new request ([Stripe idempotency reference](https://docs.stripe.com/api/idempotent_requests)). Do not collect cash/check or create a new card checkout while it is unresolved.
- A pending cash/check receipt, an open field or customer checkout, a held Stripe charge, or unreadable job money blocks another collection. Cancel an open field checkout only after the server checks Stripe and confirms it expired. If Stripe says paid, verify the original charge instead.

## Release and rollback

`EGC_FIELD_PAY_ENABLED` is **off by default**. New field collections require it to be exactly `true` **and** both `MONEY_API_ENABLED=true` and `MONEY_UNIFIED_TOTALS=true` in Cloudflare Pages. The money API requires the payment-ledger backfill before activation; unified totals has its documented shadow comparison and review gate. These prerequisites and the Stripe connection must be verified before enabling the field flag. This runbook does not authorize changing production flags or running a real charge.

Publish the reviewed `firestore.rules` and `firestore.indexes.json` to Firebase project `egcw-1ec83` from the intended merged commit **before** enabling collection: `firebase deploy --only firestore:rules,firestore:indexes --project egcw-1ec83` (see [GO-LIVE.md](GO-LIVE.md)). Cloudflare Pages has separate Preview and Production variables; saving a variable requires a new deployment. Verify the actual deployed revision and rules, then exercise authorized synthetic cases before any owner-approved live-charge acceptance test.

For rollback, turn `EGC_FIELD_PAY_ENABLED` off and redeploy to stop **new** field collections. Preserve the saved receipts, card claims, review decisions and money ledger; do not clear a hold or reverse a verified payment by changing a flag. Keep the money prerequisites available while pending receipts, Stripe sessions or CRM handoffs need verification or manager review. Resolve them from the saved job and provider evidence before considering any further flag change.

Receipt photo bytes live only in server-owned `fieldPaymentReceipts`, apart from the submitting phone's temporary retry copy. Firestore rules deny direct browser access to that collection and to submission/card-claim records. The API serves a saved photo only to an authorized owner or manager for its job, with private no-store and restrictive response headers. Crew-facing job data contains status, not photo bytes or a receipt URL. Do not put receipt images in a job document, public asset, customer message or HighLevel note.
