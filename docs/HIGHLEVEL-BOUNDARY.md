# HighLevel boundary

## Owner rule

> "don't fuck with GHL, all follow-ups and customer communication goes through high level, we just need tracking through high level" (owner, 2026-09-28)

HighLevel (GHL) owns every follow-up and every customer message. The Employee Hub (Cloudflare Pages Functions) and the Railway platform (egc-api, egc-mcp, egc-worker) track what happens. They do not run a second follow-up queue, and they never write to HighLevel as a side effect of something that is not a real send the owner turned on.

This page lists every code path that writes to HighLevel or messages a customer, with its flag and default. Every row was checked again against the code after the integration branch (FUN-13, SYNC-QUEUE, CLIENT-LOGIN, FUN-36, RECUR-CRON, FUN-30 and the rest) was merged into GHL-ALIGN on 2026-09-29. Line references are given so each row can be checked again. The same paths are registered, with their HighLevel triggers, in [automation-registry.md](automation-registry.md).

Two terms are used below. **Hub operations** is the Hub side of the signed bridge: it is on whenever `HUB_SESSION_SECRET` is 32+ characters, unless Cloudflare `EGC_OPERATIONS_ENABLED` is set to anything other than `true`. **The bridge is on** means Hub operations are on and egc-api has `EGC_OPERATIONS_ENABLED=true` (off by default; [go-live B5](GO-LIVE.md#b5-railway-platform-and-the-signed-bridge) turns it on).

## What GHL-ALIGN changed

| Change | Before | Now | Flag (default) |
| --- | --- | --- | --- |
| 6-month garage check-in | With Hub operations on, the closeout skipped the HighLevel task and egc-api opened a platform task instead (`provider-notes.ts`). A field completion only ever got the platform task. | The closeout (`functions/api/highlevel.js`) and a verified field completion (`functions/_lib/field-execution-sync.js` via `functions/_lib/highlevel-checkin.js`) create the HighLevel task instead. The closeout creates it with Hub operations off (as before), or with them on once the egc-api note is verified. A field completion creates it only while the bridge is on, after the egc-api note is verified; with the bridge off, a field-completed job gets no check-in in any system, as before. The platform task is opt-in. The Hub creates the HighLevel task only when egc-api reports no platform task, so a check-in is never in both places. A platform task opened while the flag was on is still reported after the flag is turned off. If the flag is turned on after a field completion's HighLevel attempt may already have landed, the Hub reads HighLevel before accepting the platform task: a HighLevel task found there stays the check-in, and the platform task is reported as a duplicate to cancel. With Hub operations on, every HighLevel check-in write reads the contact's tasks first and matches by title and UTC due day, so a retry never adds a second task. The due date is six months after the saved completion (else the closeout's `completed_at` or `sent_at`), in whole minutes; a closeout with none of them writes no task, because a retry could not find it again. A field completion claims the check-in on the job first, so the background sync and a manager's retry never create it twice. | `EGC_OPERATIONS_CHECKIN_TASKS_ENABLED` on egc-api (off) |
| Messaging dry run | The approved-send core upserted a HighLevel contact before its dry-run return, which could fire "contact created" workflows. | An approved-send dry run makes no HighLevel write. An unknown contact stays unknown (the result says `contact: 'unknown'`). A linked contact is only read, so the dry run still reports DND and mismatches. A real send is unchanged. Accepted-quote portal invitation retries are row 5 and ignore the dry run: a real (not preview) messaging cron tick still sends them. | `EGC_MESSAGING_DRY_RUN` on Cloudflare (dry run unless exactly `false`) |
| Inbound reconciler | Whenever egc-api operations were on and one owner was found, it opened platform review tasks every minute for unanswered customer texts, duplicating HighLevel's unread conversations. MCP `actions.reconcile_inbound` ran it on demand. | It is built, ticks and runs only with the flag. Otherwise `inbound.reconcile` and MCP `actions.reconcile_inbound` answer `inbound_tasks_disabled` ("disabled: follow-ups live in HighLevel") and create nothing. The read-only MCP tools `egc.followups_due` and `egc.whats_overdue` keep working. | `EGC_OPERATIONS_INBOUND_TASKS_ENABLED` on egc-api and egc-mcp (off) |

Every new flag is compared to exactly `true`. Any other value, including `TRUE` or `1`, leaves it off.

## Follow-up work outside HighLevel that remains

These are internal tracking, not customer messages. They are unchanged by GHL-ALIGN.

- The platform task table and the Hub Action Center, including tasks proposed from visit recordings and the MCP task tools (`actions.propose`, `actions.edit`, `actions.complete` and the rest). They create work only when a person or an explicit AI command does.
- The follow-up owner setting (`EGC_OPERATIONS_FOLLOWUP_POLICY_ENABLED`, off) and the overdue widget on the Hub home screen, which reads the same task table.
- Rebooking requests in the Hub: a customer asks in the portal and staff mark them contacted (through the server when `CUSTOMER_LIFECYCLE_API_ENABLED=true`, FUN-36). Nothing is sent to the customer.

## Owner checklist

1. Leave `EGC_OPERATIONS_CHECKIN_TASKS_ENABLED` and `EGC_OPERATIONS_INBOUND_TASKS_ENABLED` unset. HighLevel keeps the check-ins and the unanswered-text follow-ups.
2. Deploy the Hub (Cloudflare Pages) together with or before egc-api. Until the Hub change is live, a Hub with operations on still expects egc-api's platform check-in task, and a closeout would get no check-in at all.
3. The check-in task reads and creates contact tasks with the `contacts.readonly` and `contacts.write` scopes the HighLevel private integration already has ([messaging owner setup](messaging-owner-setup.md), section 2). No new scope is needed.
4. Confirm `HIGHLEVEL_API_KEY` and `HIGHLEVEL_LOCATION_ID` (or the `GHL_*` names) are set on **Cloudflare Pages**, not only on Railway. Once the bridge is on, a field completion creates its check-in from the Hub, so it needs the Pages key too. If either is missing, the completion's internal handoff shows **blocked** with "HighLevel is not configured for the Hub"; set them, then tap **Retry internal handoff** on that job. A job whose handoff shows "HighLevel refused the 6-month check-in task" needs the key's contact access or the job's linked contact checked before the retry.
5. Once the bridge is on, each verified field completion creates the HighLevel task "6-month garage check-in". Check that no HighLevel workflow triggered by **Task Added** reacts to it in a way you do not want (the [automation registry](automation-registry.md) lists this under "HighLevel Note Added / Task Added workflows").
6. Close any inbound review tasks that are still open. With `EGC_OPERATIONS_INBOUND_TASKS_ENABLED` unset, the reconciler no longer runs, including the pass that completed these tasks after staff replied, so an open one would stay open and later show as overdue on the Hub home screen and in MCP `egc.whats_overdue` and `egc.followups_due`. Such tasks exist only if the follow-up owner setting (`EGC_OPERATIONS_FOLLOWUP_POLICY_ENABLED`) was on; with it off, there are none. To check, run this read-only query on the Railway Postgres: `select id, title, due_at from tasks where dedupe_key like 'inbound_reply:%' and status in ('open','in_progress');`. Complete each one in the Hub Action Center (outcome: "Handled in HighLevel conversations"), or with MCP `actions.complete` or `actions.cancel`. Do not update the table directly: task writes must go through the operations service.
7. In the operations status (`egc.operations_status`), the `post_job_followups` row now reports new check-ins as `highlevel`: HighLevel owns them. A `pending` or `blocked` row left from before the deploy clears to `highlevel` when that job's completion handoff or closeout is retried; nothing else needs doing.
8. Turning `EGC_OPERATIONS_CHECKIN_TASKS_ENABLED` off after it was on is safe. A job that already has a platform check-in task keeps it, and the Hub adds no HighLevel task for that job. Turning it on is not recommended. If you do, turn it on only when no completion handoff or closeout sync shows error or pending. A field completion retried after the switch reads HighLevel first: if its earlier attempt did create the HighLevel task, that task stays the check-in and the job's handoff asks operations to cancel the duplicate platform task in the Action Center. A retried closeout is not checked this way.
9. In HighLevel, make sure no workflow depends on a contact being created by a messaging dry run. That no longer happens.

## How this is checked

- `tests/ghl-align.test.mjs` uses a fake HighLevel that records every request by method and path. It shows that an approved-send dry run (the core, `POST /api/messages` and a messaging cron tick) makes no HighLevel write, and that a real (not preview) cron tick still runs the accepted-quote portal invitation retry (row 5). It shows that a real send makes the same requests as before, and that closeouts and field completions create exactly one check-in task in HighLevel unless the platform reports its own. It also covers a retried closeout days later, a closeout with no stable due date (no task), a closeout over the Firestore fixture days after a field completion (anchored to the saved `completedAt`, one task), a completion time with milliseconds when HighLevel returns the due date at a coarser precision, the background sync and a manager retry running at the same time, an abandoned claim expiring after two minutes, the platform flag turned on after an uncertain HighLevel attempt (HighLevel is read, never written, before the platform task is accepted), and the blocked outcomes (HighLevel not configured on Pages, an unusable contact, a refused task).
- `egc-platform/apps/api/test/provider-notes-postgres.check.mjs` shows that egc-api opens no platform check-in task unless `EGC_OPERATIONS_CHECKIN_TASKS_ENABLED` is exactly `true`, that a task opened while it was on is still reported after it is turned off (from the event's stamp, or from the exact dedupe key if the stamp was lost), and that operations health labels HighLevel-owned check-ins `highlevel` instead of counting them as pending.
- `egc-platform/apps/api/test/inbound-optin-postgres.check.mjs`, `apps/api/src/inbound-optin.test.ts`, `apps/api/src/operations.test.ts` and `apps/mcp/src/operations.test.ts` show that the inbound reconciler is never built, never ticks and creates nothing unless its flag is exactly `true`.
- `tests/automation-registry.test.mjs` and `node scripts/automation-inventory.mjs --check` fail on any HighLevel write path that is not registered, including the check-in task in `functions/_lib/highlevel-checkin.js`.
