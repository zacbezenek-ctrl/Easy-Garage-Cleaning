## 2. Golden rules (read before editing anything)

1. **Do NOT hand-edit the generated `.html` files.** Almost every page is a
   build artifact written by `_generate_site.py`. Hand edits get overwritten on
   the next build. Edit the **source** (`_services_data.py` or
   `_generate_site.py`), then re-run the generator. See §4–§5.
2. **Do NOT touch the lead-capture form pipeline** unless that is explicitly the
   task. It is a working, revenue-critical path (Web3Forms email + Zapier SMS +
   Meta CAPI + AI text-back). See §8. If you change anything near it, **verify a
   submission end-to-end on the Cloudflare preview** before merging.
3. **Never fabricate reviews, ratings, star counts, or `AggregateRating`
   schema.** Real Google reviews only. `reviews.html` is intentionally built with
   placeholder slots + a GBP embed slot. Do not add rating schema until verified
   counts exist in Google Business Profile.
4. **Work on a branch.** Cloudflare Pages builds a per-branch preview URL, so
   production never breaks. Review the preview, confirm the lead form submits,
   then merge.
5. **Small, reviewable commits.** Report diffs and what to verify on the preview.
6. **No keyword stuffing, no fabricated claims** (e.g., "licensed and insured"
   language already lives in the data — don't invent new claims).

**Standard workflow for any content/SEO change:**
```bash
# 1. edit _services_data.py and/or _generate_site.py
python3 _generate_site.py        # 2. regenerate
git add -A && git commit -m "..." # 3. commit BOTH source and generated HTML
git push -u origin <branch>       # 4. push; review the CF preview URL
```
> Confirm with the owner whether the **Cloudflare Pages build command** runs the
> generator or just serves committed HTML. Committing both source **and**
> regenerated output keeps us correct either way. Today, the committed `.html`

## 4. Source-of-truth map (what controls what)

| To change… | Edit… |
|---|---|
| A service page (junk removal, garage cleanout, etc.) | `SERVICES` in `_services_data.py` |
| A location/town page | `CITIES` in `_services_data.py` |
| A single-item page (couch, hot tub, treadmill, fridge, shed) | `ITEM_PAGES` in `_services_data.py` (+ `SERVICE_DEFINITIONS` in generator) |
| A project / case study | `PROJECTS` in `_services_data.py` |
| A comparison page (blog/*-vs-*) | `COMPARISON_PAGES` in `_services_data.py` |
| Items we don't take | `NO_ITEMS` in `_services_data.py` |
| Pricing page & tiers | `render_pricing()` in `_generate_site.py` |
| FAQ page | `render_*`/FAQ helpers; per-page FAQs live in the data entries |
| Reviews page | `render_reviews()` + `GBP_REVIEW_URL` |
| Service-area page / town list | `AREA_SERVED`, `SERVICE_AREA_GRID`, `render_service_areas()` |
| Sitewide `<head>`, meta, schema, analytics | the page shell + schema functions in `_generate_site.py` (`business_schema()`, `service_schema()`, `faq_schema()`, etc.) |
| Sitemap | `generate_sitemap()` (URLs assembled in `main()`) |
| Brand constants (phone, email, site, GA id) | top of `_generate_site.py` (§7) |

### ⚠️ The homepage is special
`index.html` is **not** produced by a single `render_home()`. It is maintained
by a chain of regex **patch** passes over an existing `index.html`
(`patch_index_iteration6/7`, `patch_index_home_fixes`, `patch_iteration4/5_home`,
`fix_index_schema`, `patch_index_hero_premium`, …). Consequences:
- The homepage can **drift** from generator constants. Example today:
  `index.html` `areaServed` lists 9 cities (incl. Johnstown, Berthoud) while the
  generator's `AREA_SERVED` lists 7 — reconcile when touched.
- To change the homepage, edit the relevant patch function (or the base
  `index.html` the patches operate on), then re-run the generator. Test
  carefully — regex patches are brittle.

> Some legacy town pages (e.g., `garage-cleanouts-severance-co.html`,
> `garage-cleanouts-laporte-co.html`) exist as committed HTML but are **not** in
> the generator's `CITIES` data, so they aren't regenerated. Verify before
> assuming a rebuild maintains them.

## 6. SEO conventions (already in place — keep, don't duplicate)

The technical SEO foundation is **largely done**. Maintain it; don't re-create it.

- **Titles & meta** — unique per page, pattern: *term + town + brand*.
- **One H1 per page**, ordered headings.
- **Canonicals** on every page (`ensure_canonical()` enforces; blog has
  `fix_blog_canonicals()`).
- **JSON-LD** — sitewide `LocalBusiness` + `Organization`; per-page `Service`,
  `FAQPage`, `WebPage`, `BreadcrumbList`, `HowTo`, `WebSite`, `OfferCatalog`,
  `ImageGallery`. `areaServed` lists the towns.
- **Sitemap** `sitemap.xml` (built in `main()`), **robots.txt** (references the
  sitemap, blocks internal pages, has an explicit AI-crawler GEO/AIO policy).
- **GEO/AIO files:** `llms.txt`, `llms-full.txt`, `ai.txt`, `humans.txt`.
- **Internal linking** is already rich (each service has a `related` cluster +
  in-body contextual links; cities cross-link to sibling service + home).
- A built-in `audit_seo_meta()` checks for over-long titles — use/extend it.
- **Weakest area = images.** Only a few real photos exist; many before/after
  galleries are CSS placeholders. Real, descriptive-filename, alt-texted,
  compressed, lazy-loaded photos are the main genuine SEO gap.

## 8. Lead-capture form (DO NOT BREAK)

- **Form:** `<form class="lead-form-lite">`, generated by `quote_form_for()`.
  Fields: name, phone, items; hidden `source`, `subject`, Meta attribution
  (`fbc/fbp/fbclid/landing_url/referrer`), and a `botcheck` honeypot.
- **Primary submit:** native POST to **Web3Forms** (`FORM_KEY` in generator) →
  email. This is the source-of-truth lead.
- **Mirror leg:** `fb-capture.js` fires a fire-and-forget POST to
  **`/api/web-lead`** (Cloudflare Function) → **Zapier Catch Hook**
  (`WEBSITE_LEAD_HOOK_URL` env) → team SMS + **Meta CAPI** Lead + AI text-back in
  "Tyler's voice" via OpenPhone. Server computes `lead_first_name`,
  in/out-of-hours, and E.164 phone for the Zap.
- **Hardening:** origin allow-list, 32 KB body cap, honeypot returns fake
  success, phone validation, `no-store`. `_headers` sets `fb-capture.js` to
  `no-cache` so the relay can't silently go stale. Bump the `?v=` on the script
  ref to bust caches.
- **Health probe:** `GET /api/web-lead` reports `{configured: true|false}`.

**To verify after any change:** load a preview page, submit the form with a real
name + phone, confirm (a) the success/thank-you path, (b) the Web3Forms email
arrives, and (c) `GET /api/web-lead` returns `configured: true`.

Timnath, Wellington, Severance, LaPorte. (Homepage schema also references
Johnstown & Berthoud — reconcile.)

owner says otherwise):**

1. **Homepage keyword.** Playbook wanted H1 = "junk removal fort collins."
   The brand/site is built around **garage cleanouts / one-day turnaround**.
   *Default: keep garage-cleanout positioning.*
2. **Pricing model.** Playbook references an "offer ladder," a **20% overage
   clause**, and a **cubic-yard reference** — **none of which exist in this
   repo.** Live model is a flat-rate ladder: **$400–$3,500** garage cleanouts
   (Clear-out $400–650 · Full $650–1,200 · Turnaround $1,200–2,200 ·
   Whole-property $2,200–3,500) + per-item ranges ($99–150 single item, etc.).
   *Default: keep existing tiers; do NOT invent overage/cubic-yard terms.*
   **Needs owner data** to adopt the playbook's model.
3. **Street address.** Schema currently publishes **746 Star Grass Ln, Fort
   Collins, CO 80525** sitewide. Playbook wanted a service-area business with **no
   street address**. *Default: keep current (status quo, lower risk); owner to
   decide GBP posture.*
4. **Brand palette.** See §7. *Default: keep current palette.*
5. **Missing towns.** **Berthoud, Bellvue, Livermore** have no pages and lack
   real local detail. Don't generate thin doorway clones — add to `CITIES` only
   with genuine neighborhoods/landmarks/a real local job example from the owner.
